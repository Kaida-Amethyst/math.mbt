# 如何向使用者展示数值可靠性

> 状态：暂时搁置
>
> 最后更新：2026-08-13

## 背景

math.mbt 已经开始为 stable 数值函数建立契约、独立 oracle、边界语料和跨后端测试。
这些工作能够帮助维护者判断实现是否满足契约，但“已经做过验证”和“使用者能够感受到
并检查这种可靠性”并不是同一件事。

最初尝试为 `exp` 编写一份详细认证记录，列出工具版本、资产哈希、语料构成、测试结果、
复现命令和证据边界。内容虽然完整，却更像审计底稿：普通读者需要阅读较长文字，才能
提炼出契约、最大误差和验证范围。把正文改写成解释性文章后，这个问题仍然存在。当前
判断是，继续润色文字未必能够有效建立信任。

因此，`docs/reliability/` 暂时移除。认证报告最终采用什么形式，留待重新设计；现有 oracle、
固定语料和测试不受此决定影响。

## 当前建立的判断

人通常更容易从少量关键数字、表格和图形中形成第一判断。可靠性页面首先应该让读者一眼
看到：函数承诺什么、测了多少输入、最大观测误差是多少、是否存在越界，以及证据最后一次
更新在何时。长篇方法说明更适合作为按需展开的附录。

可视化本身不能代替证据。图表中的每个数字仍应绑定被测提交、oracle 版本、随机种子和
原始结果，并能回到可复现的命令或机器可读报告。否则图表只是更容易阅读的主张，而不是
更强的验证。

还必须区分契约与观测结果。例如“全部 `ULP = 1` 的输入”只能指某次明确语料中观测到的
全部案例，不能暗示已经穷举所有 binary64 输入。

## 可能的页面结构

### 结果摘要

在页面顶部用一张小表展示最重要的结果：

| 指标 | 示例内容 |
|---|---|
| 精度契约 | 不超过 1 ULP |
| 固定 oracle 语料 | 输入数量和 oracle 名称 |
| 支持后端 | 各后端 debug/release 结果 |
| 最大观测误差 | 0、1 或更大 |
| 超过契约的结果 | 数量 |
| 外部困难输入 | 语料来源和输入数量 |
| 最后认证 | 日期、Git 提交和 CI 运行链接 |
| 尚未完成 | 例如外部再认证尚未自动化 |

表格应同时展示成功和缺口，避免只给出一个含义不清的绿色徽章。

### ULP 误差分布

对固定语料统计 `ULP = 0`、`ULP = 1` 和 `ULP > 1` 的实际数量，并用简单柱状图展示。
这种分布比“测试通过率”更有解释力：它既能显示大多数结果是否正确舍入，也能直接暴露
触及或超过契约边界的案例。

当前 `exp` 测试只计算最大误差，还不能生成完整分布。需要先由报告工具重新统计，不能从
已有的最大值推断各档数量。

### 最坏案例表

页面可以列出固定语料中全部达到最大 ULP 的输入，至少包含：

- 便于人理解的十进制输入；
- 保证精确复现的输入位模式；
- 输入所属区域，例如参数缩减边界或次正规结果区域；
- oracle 期望位模式与实际位模式；
- ULP 距离、后端和案例来源。

如果案例很多，正文只展示区域统计和代表案例，完整列表以 CSV 或可折叠表格提供。

### 输入区域覆盖

`exp` 的随机位模式大部分可能直接落到正零或正无穷，样本数很大也未必深入有效计算区域。
报告可以按特殊值、下溢边界、次正规结果、正常结果、参数缩减边界和上溢边界分组，分别
展示样本数、最大 ULP 和越界数。这样读者能够判断测试是否覆盖实现真正危险的位置。

## 每日随机审计的设想

可以建立定时 CI，每天用 MPFR 对照十万项新的确定性随机输入，并公开最新结果和累计趋势。
它的价值是持续搜索尚未进入固定语料的反例，以及让验证状态绑定到近期提交，而不是用一份
静态文档长期宣称“曾经测试通过”。

每日输入不能采用没有结构的均匀随机。候选分层包括：

- 正常输出区域中的随机数；
- 次正规结果区域；
- 上溢和下溢转换的邻域；
- 参数缩减单元边界的邻域；
- 按指数和尾数分层的位模式；
- 已知最坏案例附近的变异输入。

每次运行必须记录种子、被测提交、工具版本、各分层数量、最大 ULP 和所有越界案例。
发现 `ULP > 1` 时 CI 应失败并保存完整输入；确认后的反例需要缩减并加入永久回归语料。

每日随机审计是持续发现机制，不能取代固定边界语料、外部困难输入或形式化证明。十万只是
初始规模，最终数量应根据实际运行时间和发现效率决定。

## 报告产物的可能形式

一个报告器可以从同一次测试生成：

```text
exp-report.json
exp-worst-cases.csv
exp-ulp-distribution.svg
```

JSON 保存机器可读的运行元数据和统计；CSV 允许检查全部最坏案例；SVG 或静态 HTML 用于
GitHub Pages 和文档展示。页面还可以记录每日最大 ULP、累计测试输入数和累计越界数，失败
发生后保留历史，而不是被下一次绿色结果覆盖。

不建议让定时任务每天向主分支提交报告文件，这会制造大量无关提交。可以由 CI 发布
GitHub Pages 或保留带提交号的构建产物；具体保存期限和历史策略仍需决定。

## 可能的实施顺序

1. 先为现有 24,697 项 `exp` 固定语料编写报告器，得到真实的 ULP 分布、区域统计和最坏
   案例列表；
2. 根据实际数据设计一页最小仪表盘，判断哪些图表确实帮助理解；
3. 把报告格式接入外部 oracle 再认证，使每个数字都链接到对应提交和原始产物；
4. 再增加每日分层随机审计和历史趋势；
5. 形成可复用模板后，再应用于后续晋升的数值函数。

## 尚未决定的问题

- 可靠性页面应留在仓库 Markdown，还是发布为 GitHub Pages；
- 哪些图表属于每个函数都必须提供的最低集合；
- 固定语料中的所有 1 ULP 案例是否长期保存，还是只保存代表案例和完整下载文件；
- 每日随机审计的样本分层、数量、运行后端和失败门禁；
- CI 历史产物保存多久，以及怎样把报告稳定绑定到发布版本；
- 认证材料是否需要独立维护者审阅，以及如何公开记录该审阅。
