# Q-01. 稳定 API 的语义裁判顺序 〔已解决〕

> 最后更新日期：2026-08-12
> 仓库：Kaida-Amethyst/math.mbt
> 记录者：Codex

## 问题描述

可靠性基线需要先确定判断函数行为是否正确时采用哪一套标准。IEEE 754/C23、MoonBit Core 以及移植来源的既有行为可能不完全一致，因此必须先确定裁判顺序，后续函数契约和测试才能使用同一基准。

## 建议的解决方案

### A1. IEEE 754/C23 为底线，MoonBit Core 兼容为目标 【已采纳】

#### 方案描述

浮点基础语义以 IEEE 754/C23 为底线，尤其是 NaN、signed zero、无穷、舍入和相邻浮点数；与 MoonBit Core 重叠的 API 尽量保持兼容。发生冲突时先满足明确的标准语义，再记录与 MoonBit Core 的差异。特殊函数另行参考成熟实现和数学惯例。

仓库当前文档和实现只能证明“现在写了什么、做了什么”，不能单独裁定“正确行为是什么”。标准没有直接覆盖的函数，应优先寻找功能和抽象层级相同的权威外部库，以其公开文档、规范文本和回归测试形成可追溯的契约；只有外部参照确实分歧或缺失时，才提出项目自有策略，并明确标记这部分选择。

#### 优点

- 语义基础公开、稳定，能够与成熟测试集和其他语言实现对照。
- 仍然把 MoonBit 生态兼容作为明确目标。
- 避免把某个上游实现的偶然行为直接当成库的长期契约。

#### 缺点

- 当 MoonBit Core 与标准语义不一致时，需要维护差异说明。
- 特殊函数不完全由 IEEE 754/C23 覆盖，仍需逐族制定契约。

### A2. MoonBit Core 行为优先

#### 方案描述

凡是 MoonBit Core 已提供的重叠 API，优先复制其当前行为；只有 Core 没有覆盖时才采用 IEEE 754/C23 或其他参考。

#### 优点

- MoonBit 用户在替换包时较少遇到行为差异。

#### 缺点

- Core 的当前实现行为未必等于稳定、明确的公共规范。
- 可能使跨语言验证和标准测试集复用变得困难。

## 最终采用方案

A1. IEEE 754/C23 为底线，MoonBit Core 兼容为目标
