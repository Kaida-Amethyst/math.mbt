# Q-12. R0 回归测试的组织方式 〔已解决〕

> 最后更新日期：2026-08-12
> 仓库：Kaida-Amethyst/math.mbt
> 记录者：Codex

## 问题描述

当前 67 个测试全部与实现放在源码文件中，没有 `*_test.mbt` 黑盒测试。R0 需要确定新增回归测试放在哪里，从而区分用户可见契约与内部实现不变量。

## 关联问题

1. [Q-03. ULP 距离的语义契约](Q-03-ulp-distance-contract.md)（依赖：ULP 编码细节需要内部测试）
2. [Q-14. R0 的完成门槛](Q-14-r0-exit-criteria.md)（依赖：采用的测试层次将成为完成条件）

## 建议的解决方案

### A1. 公共契约用黑盒测试，内部数值工具用白盒测试 【已采纳】

#### 方案描述

`roundeven`、`clamp`、`norm`、`logsumexp`、`nextafter` 和 `pown` 的回归案例放入 `*_test.mbt`，从包外用户视角调用公共 API；ULP 有序编码和断言辅助函数放入 `*_wbtest.mbt`。现有大批数值样本测试暂时保留，后续再逐步整理。

#### 优点

- 公共契约不会因访问私有实现而产生虚假通过。
- 内部位操作仍能获得细粒度验证。
- R0 不需要同时重写全部历史测试。

#### 缺点

- 短期内会并存内联、黑盒和白盒三种测试布局。
- 需要避免同一反例在多个层次重复维护。

### A2. 保持现有内联测试方式

#### 方案描述

继续把新增测试放在对应实现文件中，不引入新的测试文件类型。

#### 优点

- 修改量最小，测试和实现位置接近。

#### 缺点

- 无法证明公共 API 从包外使用时的可见性和行为。
- 公共契约与实现细节继续混在同一层次。

## 最终采用方案

A1. 公共契约用黑盒测试，内部数值工具用白盒测试
