# Q-04. ULP 测量函数是否保留为公共 API 〔已解决〕

> 最后更新日期：2026-08-12
> 仓库：Kaida-Amethyst/math.mbt
> 记录者：Codex

## 问题描述

`ulp_error` 和 `ulp_error_f32` 当前属于公共 API，但仓库内只有 ULP 断言辅助函数调用它们，没有其他生产逻辑依赖。R0 需要决定二者是稳定的用户能力、实验性工具，还是应收回为内部测试基础设施。

## 关联问题

1. [Q-03. ULP 距离的语义契约](Q-03-ulp-distance-contract.md)（依赖：无论可见性如何，内部使用前都必须先确定语义）
2. [Q-13. R0 是否清点全部公共 API 的成熟度](Q-13-public-api-inventory.md)（一般关系：ULP 函数是 stable/experimental/internal 分类的具体案例）

## 建议的解决方案

### A1. 从主库公共 API 收回，作为内部验证工具 【已采纳】

#### 方案描述

移除 `ulp_error` 和 `ulp_error_f32` 的公共可见性，只供库内 ULP 断言和验证代码使用。若未来确认用户确有测量需求，再以名称和特殊值契约都更明确的验证 API 或独立测试包重新公开。收回行为需要在版本说明中明确标记为接口变更。

#### 优点

- ULP 距离主要是测试度量，不是数学函数库必须承诺的运行时能力。
- NaN、无穷、跨符号距离和饱和方式都带有测试策略色彩；内部化后可以继续修正表示而不冻结公共契约。
- 避免用户把“两个 NaN 距离为 0”误解为通常意义上的数值距离。
- 当前仓库内调用均属于测试辅助，收回不会扰动其他生产实现。

#### 缺点

- 已发布版本中它们已经出现在公共接口，收回可能破坏未知的外部调用者。
- 外部项目若希望复用同一 ULP 判定逻辑，需要自行实现或等待独立验证 API。

### A2. 保留为 experimental 公共工具

#### 方案描述

继续公开两个函数，但明确标记为 experimental，不承诺名称、返回类型和特殊值策略长期稳定。

#### 优点

- 不立即打断可能存在的外部调用者。
- 用户可以复用与本库相同的误差测量方法。

#### 缺点

- 主包公共面继续混入测试基础设施。
- MoonBit 的包文档和调用体验未必能让 experimental 边界足够醒目。

### A3. 作为 stable 公共 API 保留

#### 方案描述

把 Q-03 采用的距离契约作为长期公共承诺，继续由主库导出两个函数。

#### 优点

- 对现有外部调用完全兼容。
- 用户能够直接使用库内同一把 ULP“尺子”。

#### 缺点

- 会冻结具有测试策略色彩的特殊值语义和返回表示。
- 未来若改用更适合大距离的类型或重新定义 NaN 行为，将形成破坏性变更。

## 最终采用方案

A1. 从主库公共 API 收回，作为内部验证工具
