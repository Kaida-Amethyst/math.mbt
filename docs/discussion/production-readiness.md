# 生产可用性：问题清单与建议路径

状态：讨论稿  
日期：2026-08-12

## 当前判断

这个库已经具备相当可观的实现规模，也有真实用户，但目前更接近一个覆盖面较广的数值算法移植集，还不能把全部公共 API 作为一个整体承诺为“生产可用”。

问题不在于代码完全不可用。现有 67 个测试可以在 wasm、wasm-gc、JavaScript 和 native 后端通过，CI 也已经覆盖格式、静态检查以及 debug/release 测试。真正的缺口是：公共 API 的覆盖范围远大于可靠性证据的覆盖范围，而且已有若干基础边界错误能够绕过现有测试。

因此，后续工作的重点不应继续放在增加函数数量，而应转向建立一条能够持续回答下列问题的证据链：

1. 一个函数在各种特殊输入下应当返回什么？
2. 实现与独立参考结果相差多少？
3. 这种行为在所有支持的后端上是否一致？
4. 一次代码或工具链升级有没有破坏原有承诺？
5. 用户安装的包究竟对应哪个经过验证的源码版本？

## 什么叫生产可用

对这个库而言，“生产可用”至少包含五层含义：

- **语义明确**：每个稳定 API 对 NaN、正负零、无穷、次正规数、定义域错误、溢出和下溢都有明确约定。
- **数值可信**：精度结论来自可复现的独立比较或性质验证，而不只是少量手写样本。
- **后端一致**：wasm、wasm-gc、JavaScript 和 native 的差异已知、受测，并在文档中说明。
- **变更受控**：稳定 API 的语义、精度或兼容性退化会被自动门禁发现。
- **发布可追溯**：包版本、Git tag、源码提交、工具链版本和测试报告能够一一对应。

生产可用并不要求所有函数都达到同一成熟度。更现实的方式是先形成一个可靠核心，再逐步扩大稳定范围。

## 已确认的问题

### 1. 正确性问题已经实际存在

使用最小回归探针已经复现以下问题：

- `roundeven(-1.5)` 返回 `-1`，而不是最近的偶数 `-2`。
- `clamp` 在上下界为 NaN 时可能返回有限值，与当前文档约定冲突。
- `norm([0.0, 0.0])` 返回 NaN；包含无穷分量的向量也可能返回 NaN。
- `logsumexp([-∞, -∞])` 返回 NaN，而合理结果应为 `-∞`；空数组还缺少明确契约。
- `nextafter` 把低 32 位作为有符号整数比较，在特定位模式边界上会向错误方向移动。
- `pown` 对最小 `Int` 指数取负时溢出，可能直接返回错误结果。
- Double 版本的 `ulp_error(-0.0, 0.0)` 发生整数溢出并返回负值。

这些问题说明，现有测试通过只能证明当前样本未失败，不能证明公共 API 的边界语义已经可靠。

### 2. 精度测量基础本身有缺陷

当前 `ulp_error` 直接对有符号 IEEE 754 位模式做减法和绝对值，没有先构造保持浮点数序关系的整数表示。跨符号位时可能溢出，而 `assert_ulp` 只检查结果是否大于阈值，负溢出可能被当成成功。

这意味着 README 中的最大 ULP 表目前不能被解释为严格的误差保证。即使修复测量器，表中数据仍需要补充：

- 参考实现及其版本；
- 输入集合及生成方法；
- 测量覆盖的区间和特殊值；
- 被测后端、编译模式和工具链；
- 最坏输入、期望值和实际值；
- 报告的可重复生成方式。

### 3. 测试覆盖分布不合理

当前仓库大约有 152 个公共函数和 67 个内联测试块，没有 `*_test.mbt` 黑盒测试。覆盖率分析结果为 1520/2355，约 64.5%，并且有 99 个文件存在未覆盖代码。

比总覆盖率更重要的是，一批已经公开的函数为零行覆盖，包括部分 Airy、Bessel、Incomplete Gamma、`nextafter`、`norm` 和 `logsumexp` 实现。现有 62 个 `moonbit nocheck` 文档示例也没有参与文档测试。

因此需要区分三种测试职责：

- 黑盒测试验证用户真正能够看到的公共契约；
- 白盒测试验证位操作、范围缩减和 ULP 工具等内部不变量；
- 独立差分测试负责大规模数值精度验证。

### 4. 公共契约尚未统一

仓库目前没有明确说明以哪一套规范作为基础：IEEE 754、C23 `math.h`、MoonBit Core，还是各上游算法原本的行为。不同实现来源的特殊值处理可能互不一致。

例如，`fma` 的文档称其为单次舍入的融合乘加，但多个后端实际上执行普通的 `a * b + c`。这是契约与实现不一致，不只是精度优化尚未完成。

需要为稳定函数明确：

- 特殊值和定义域语义；
- signed zero 是否需要保留；
- 精度等级；
- 是否要求正确舍入、单调性或后端逐位一致；
- 无法满足统一契约时的后端差异。

### 5. CI 尚未形成可信门禁

现有 CI 的方向是正确的，但仍有几个缺口：

- `macos-13` 已无法正常获得运行器，使最新默认分支工作流在其他任务全部成功后仍被取消。
- 默认分支没有保护规则，也没有强制通过状态检查。
- MoonBit stable 通过在线安装脚本获取，历史构建不能完整复现。
- bleeding 和 pre-release 检查被注释，无法提前发现下一版工具链回归。
- CI 没有数值差分、覆盖率门槛、公共 API 兼容性或包安装冒烟测试。

### 6. 发布不可追溯

源码中的版本、Mooncakes 上的版本和 GitHub 发布状态没有形成一一对应关系。仓库没有 Git tag 和 GitHub Release，也没有 changelog。用户无法从包版本准确找到对应提交、验证环境、已知限制和精度报告。

曾经已有用户报告发布版不能在最新工具链运行。这说明工具链兼容范围和发布过程需要从临时响应转为正式制度。

### 7. 来源与维护信息不足

README 笼统说明实现参考或移植自 glibc、Boost、Cephes、SciPy 和其他 libm，但没有为各函数记录具体上游文件、版本或 commit、许可证以及 MoonBit 侧修改。

这同时影响法律审计和技术审计：无法确认某个常量、特殊分支或误差界究竟来自哪个版本的上游实现。

项目也高度依赖单一维护者。生产可靠性最终还需要贡献规范、数值代码审查清单、缺陷响应方式和第二位熟悉实现的审阅者。

## 总体策略

### 缩小承诺，而不是一次认证全部 API

建议将公共能力划分为三层：

- **stable**：契约明确，具有边界测试、独立参考验证、跨后端测试和公开精度报告。
- **experimental**：允许用户尝试，但不承诺完整精度和长期兼容性。
- **internal**：只服务于实现，不作为用户依赖面。

第一批 stable API 应优先选择基础且高频的函数。特殊函数只有在补齐独立参考测试后再逐组晋升。现有 API 在完成分类前不宜继续扩张。

### 先修“尺子”，再用尺子测算法

ULP 测量、参考数据生成和测试运行方式是整个可靠性工作的基础。如果这些工具有错，继续扩充固定样本只会制造错误的安全感。

### 让证据成为发布产物

精度报告不应是人工维护的 README 表格。它应由固定版本的工具自动生成，至少包含最大 ULP、最坏输入、参考值、实际值、目标后端和工具链，并作为 CI artifact 和 Release 附件保存。

## 建议路径

### 阶段 0：建立可靠性基线

目标不是立刻修完所有函数，而是确保以后发现的问题不会再次静默出现。

交付物：

1. 写出第一批基础函数的语义基线，明确参考规范和特殊值规则。
2. 修复并独立测试 `ulp_error`/`ulp_error_f32`，覆盖正负零、跨零、相邻值、无穷和 NaN。
3. 将已经确认的最小反例转为永久回归测试；公共行为使用黑盒测试，内部 ULP 工具使用白盒测试。
4. 移除失效的 `macos-13` CI 项，恢复默认分支绿色状态。
5. 生成公共 API 清单，记录每个函数的契约状态、测试状态、参考来源和后端支持情况。

完成判据：

- 已知反例先能够稳定失败，修复后在所有支持后端通过；
- ULP 测量器有独立、可审阅的正确性测试；
- 默认分支 CI 为绿色；
- 每个公共函数至少有明确的成熟度分类，而不是默认为可靠。

### 阶段 1：形成可靠核心

从基础函数中选取第一组 stable 候选，逐个补齐：

- 特殊值和分段边界测试；
- 独立参考实现的差分测试；
- 随机与性质测试；
- debug/release、所有目标后端的比较；
- 自动生成的精度报告；
- 可执行文档示例。

这一阶段应同时修正 `fma` 一类契约与实现不一致的问题：要么实现真正的融合语义，要么更名并诚实记录后端限制。

### 阶段 2：建立发布纪律

可靠核心形成后，再发布第一个带明确稳定范围的版本：

- Mooncakes 版本对应唯一 Git tag 和 GitHub Release；
- Release 包含 changelog、支持工具链范围、稳定 API 清单、已知限制和精度报告；
- CI 验证版本号、生成接口和 tag 一致；
- 默认分支启用保护和必需检查；
- 增加最低支持版本、当前稳定版和定时预发布工具链测试。

### 阶段 3：逐族认证特殊函数

按函数族推进，而不是零散补测试，例如：

1. 三角、指数和对数；
2. 舍入、分类和相邻浮点数；
3. 范数、概率辅助函数；
4. erf、gamma 及其逆函数；
5. Bessel、Airy、zeta 等特殊函数。

每一族满足 stable 门槛后再修改成熟度状态并发布。新增函数也必须同时提交契约、参考来源、测试和误差报告，不能先暴露 API、以后再补可靠性。

### 阶段 4：补齐维护与来源治理

- 增加 `THIRD_PARTY_NOTICES`，记录逐函数来源和本地修改。
- 增加 `CONTRIBUTING.md`、数值代码审查清单、Issue/PR 模板和安全报告方式。
- 建立 API 兼容性与性能回归检查。
- 培养至少一位能够审阅数值实现和测试方法的共同维护者。

## 建议首先做什么

建议第一个正式工作包命名为“可靠性基线”，而不是直接开始大规模修函数。顺序如下：

1. 选定一小组需要立即固定语义的 API：`ulp_error`、`roundeven`、`clamp`、`norm`、`logsumexp`、`nextafter` 和 `pown`。
2. 对这些 API 写下最小契约，解决哪些结果是明确错误、哪些属于待决定的策略问题。
3. 把已经发现的反例写成永久测试，先观察它们失败。
4. 第一笔实现修复只处理 ULP 测量器，因为后续所有精度声明都依赖这把“尺子”。
5. 再逐个修复其余基础函数，并在所有后端运行回归测试。
6. 同一个工作包中清理 `macos-13`，使默认分支重新显示可信的绿色状态。

这个入口有三个优点：范围有限、结果可验证，并且会同时改善算法判断能力和仓库的外部可信信号。

## 待讨论的问题

1. stable 契约主要以 IEEE 754/C23 为基线，还是优先追随 MoonBit Core？两者冲突时如何处理？
2. 第一批 stable API 的范围应当多小？是否先排除所有特殊函数？
3. 各后端需要逐位一致，还是只要求满足同一语义和误差上界？
4. `fma` 在无法真正融合的后端应当退化、报错、标记为 experimental，还是不提供？
5. experimental 状态通过文档表达即可，还是应该在包/API 结构上明确隔离？
6. 独立参考测试应放在主仓库，还是建立单独的验证工具与数据仓库？
