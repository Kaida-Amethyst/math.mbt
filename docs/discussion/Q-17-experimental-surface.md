# Q-17. experimental 状态在 R0 中如何呈现 〔已解决〕

> 最后更新日期：2026-08-12
> 仓库：Kaida-Amethyst/math.mbt
> 记录者：Codex

## 问题描述

Q-13 已决定在 R0 中建立全量公共 API 成熟度清单，并区分 stable、experimental 和 internal，但尚未决定这些状态如何向用户呈现和产生约束。这个问题会影响 R0 是以低破坏性的清单起步，还是立即调整包与导入结构。

## 关联问题

1. [Q-04. ULP 测量函数是否保留为公共 API](Q-04-ulp-api-visibility.md)（一般关系：internal 状态需要通过真实可见性收回，而不只是文档标签）
2. [Q-13. R0 是否清点全部公共 API 的成熟度](Q-13-public-api-inventory.md)（来源：全量清单已经决定，本问题补充其对用户生效的方式）
3. [Q-14. R0 的完成门槛](Q-14-r0-exit-criteria.md)（依赖：成熟度清单需要有可检查的呈现方式）

## 建议的解决方案

### A1. R0 先以可审计清单呈现，internal 同步收回可见性 【已采纳】

#### 方案描述

在仓库中建立一份作为单一事实源的 API 成熟度清单，逐项记录 stable、experimental 或 internal 以及支撑证据。R0 不重排现有包结构：缺少完整证据的公共函数先标为 experimental；达到门槛后才晋升 stable；被定为 internal 的实现或测试工具则实际移除公共可见性。

包结构隔离可以在清单稳定并掌握真实依赖面后另行评估，不作为 R0 的前置改造。

#### 优点

- 不用在修复可靠性基线之前制造大规模导入路径变更。
- stable 的范围和证据缺口立即可见，并能纳入 R0 验收。
- internal 不会停留在口头标签，而是由可见性真实约束。

#### 缺点

- experimental 仍属于可导入的公共 API，编译器不能阻止用户依赖。
- 用户是否注意到成熟度状态，取决于清单和 API 文档是否足够醒目。

### A2. R0 立即通过包或命名空间隔离 experimental

#### 方案描述

把 stable 与 experimental 放入不同的包、命名空间或导入入口，使成熟度直接反映在调用路径上；internal 完全不导出。

#### 优点

- 用户在代码中能直接看出依赖了哪一层能力。
- 后续可以对 stable 入口施加更严格的兼容约束。

#### 缺点

- 会立即改变大量现有导入和调用路径，形成显著兼容成本。
- 在 API 证据尚未清点完成前设计包边界，容易随后再次迁移。
- 会扩大 R0 范围，分散对已知正确性缺陷和测试尺子的投入。

## 最终采用方案

A1. R0 先以可审计清单呈现，internal 同步收回可见性
