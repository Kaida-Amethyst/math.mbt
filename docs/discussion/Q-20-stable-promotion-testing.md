# Q-20. stable API 的晋升测试门槛 〔已解决〕

> 最后更新日期：2026-08-12
> 仓库：Kaida-Amethyst/math.mbt
> 记录者：Codex

## 问题描述

如果所有尚未认证的公共 API 初始都位于 experimental，那么“通过测试后移入 stable”必须具有可重复、可审查的含义。单纯要求当前测试绿色不足以证明数值函数可靠：测试可能遗漏特殊值和分段边界，也可能与被测实现共享同一错误来源。这个问题需要为不同类型的函数确定证据层次、误差尺度、输入构成和跨后端要求，但不规定外部 oracle 在发布流程中的运行方式，该边界由 Q-21 决定。

## 建议的解决方案

### A1. 按函数族建立分层的可执行证据门槛 【已采纳】

#### 方案描述

每个函数或最小函数族只有同时满足以下适用条件，才能移入 stable：

1. **契约证据**：先依据 Q-01 的裁判顺序写清特殊值、定义域、signed zero、分段边界和舍入行为，并从包外视角写成纯 MoonBit 黑盒测试。
2. **独立参考证据**：对近似数值函数，使用独立高精度 oracle 生成固定输入和期望位模式；语义参考与数值参考分开选择，C23、成熟库文档可以裁定行为，高精度结果优先由 MPFR 或 Arb 一类工具生成。不能只用移植来源的同一份算法反向验证自己。
3. **性质证据**：在适用时测试单调性、奇偶性、值域、逆关系或恒等式。性质测试补充参考样本，但不代替独立 oracle。
4. **后端证据**：wasm、wasm-gc、JavaScript 和 native 的 debug/release 测试都满足 Q-11 的共同语义和误差界；必要的逐位差异必须固化并说明。
5. **回归证据**：外部差分搜索、随机搜索或人工分析找到的最坏案例一律转成永久、确定性的 MoonBit 回归测试。
6. **依赖证据**：候选函数族的公共依赖已经 stable，其他共享依赖只进入职责明确的 internal 包；实现、测试和用户文档作为一个变更一起晋升。

误差尺度按问题选择，不能统一套一个 epsilon：分类、舍入、位操作、signed zero 和特殊值使用精确位模式；普通有限近似结果记录最大 ULP；接近零、消去或下溢区域增加绝对误差；远离零且动态范围很大时再使用相对误差。每个函数族必须明确自己的适用尺度和上界。

输入至少覆盖 IEEE 754 分类、每个分段边界及其相邻浮点数、幂与指数极值、固定种子的分层随机位模式，以及已经发现的最坏案例。样本数或覆盖率百分比可以用于发现缺口，但不能单独作为晋升依据。上述证据直接体现在测试、固化数据和生成元数据中，不再维护一份逐 API 的独立成熟度清单。

#### 优点

- “通过测试”被拆成可以审查的不同证据来源，减少同源实现互相证明的风险。
- 测试尺度随函数性质变化，不会让全局 epsilon 掩盖 signed zero、下溢或巨大相对误差。
- 外部搜索发现的失败会沉淀为纯 MoonBit 永久回归，可靠性能够累积。
- 晋升门槛由可执行资产表达，不需要额外维护繁重的成熟度表格。

#### 缺点

- 为每个函数族建立独立参考数据和边界输入需要持续投入。
- 某些特殊函数的权威契约和合理误差上界仍需逐族研究，不能由统一规则自动给出。
- 四后端与两种构建模式会显著增加认证运行量。

### A2. 只以现有测试全部通过作为晋升条件

#### 方案描述

函数在当前仓库测试全部绿色后即可移入 stable，不额外要求独立参考、性质测试、分层输入或明确误差界。

#### 优点

- 晋升流程简单，短期内可以快速扩大 stable 表面。

#### 缺点

- 现有测试和被测实现可能共享错误来源，绿色结果不能证明数值正确。
- 特殊值、分支相邻点和跨后端差异容易继续遗漏。
- 不同函数使用的隐含精度标准无法被用户或维护者审查。
