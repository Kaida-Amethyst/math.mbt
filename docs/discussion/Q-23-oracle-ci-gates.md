# Q-23. 外部再认证的触发频率与门禁范围 〔待讨论〕

> 最后更新日期：2026-08-13
> 仓库：Kaida-Amethyst/math.mbt
> 记录者：Codex

## 问题描述

即使接受 CI 证据分层，仍需独立决定各层在普通 PR、相关实现变化、定期审计和发布时的执行频率，以及哪些结果必须阻止合并或发布。固定 MPFR 语料再生成和百万级困难输入审计的成本不同，不能只凭“越多越可靠”决定门禁。

## 建议的解决方案

### A1. 按成本和风险采用混合触发策略 【建议采纳】

#### 方案描述

纯 MoonBit 常规测试在每个 PR 和目标分支 push 上执行，并作为必需合并检查。固定 oracle 再认证在实现、内部浮点依赖、生成器、固化语料或公开数值契约变化时执行，同时支持手动触发；相关变更只有再认证通过才能合并。

CORE-MATH 等全量困难输入审计通过定时任务和手动任务执行，并在算法、误差界或上下溢路径发生实质变化以及发布 stable 版本前作为门禁。该任务应固定外部语料提交和内容哈希，使用不会覆盖仓库固化文件的分批脚本，并上传机器可读报告和人类可读摘要。没有影响数值实现的普通文档或维护性 PR 不强制等待全量审计。

常规 CI 可以跟随 stable MoonBit 工具链检查生态兼容性；用于认证记录的任务应固定工具链和 oracle 版本，使历史结果可复现。认证状态应绑定被测 Git commit，不能用定时任务在旧提交上的绿灯替代待发布提交的结果。

#### 优点

- 高频检查覆盖日常回归，重型审计集中在高风险变化和发布节点。
- 相关实现无法在没有 oracle 再认证的情况下合并。
- 固定认证环境与日常最新 stable 环境分别服务于可复现性和生态兼容性。
- 不相关 PR 不必为百万级语料承担时间和外部依赖成本。

#### 缺点

- 需要准确维护路径条件；隐藏依赖若未列入触发范围，可能漏跑再认证。
- 条件性必需检查在 GitHub 分支保护中需要谨慎配置，避免任务被跳过后一直等待。
- 定时全量审计发现问题时，缺陷可能已经存在一段时间。

### A2. 所有 CI 层在每个 PR 上执行 【不建议】

#### 方案描述

无论改动范围，每个 PR 都重新生成固定 oracle 语料，并执行全部外部困难输入审计；所有结果均作为合并门禁。

#### 优点

- 触发规则简单，不会因为路径过滤遗漏隐藏依赖。
- 每个合并提交都能获得同等范围的即时外部审计结果。

#### 缺点

- 所有 PR 都需要外部 C 工具链和大型语料，显著增加等待时间、故障面和资源成本。
- 文档或无关修改也被重型数值审计阻塞。
- 第三方下载或运行环境波动会频繁影响普通贡献流程，但不会增加对应改动的实际可信度。
