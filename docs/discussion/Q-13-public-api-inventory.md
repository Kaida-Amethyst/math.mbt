# Q-13. R0 是否清点全部公共 API 的成熟度 〔已作废〕

> 最后更新日期：2026-08-12
> 仓库：Kaida-Amethyst/math.mbt
> 记录者：Codex

## 问题描述

建议路线要求把公共能力分为 stable、experimental 和 internal。当前 `moon info` 生成的接口包含 200 个公共符号，其中有 166 个函数和 34 个常量。R0 需要决定是否立即为全部公共符号建立清单，还是只处理首批函数。这里的清点只记录状态和证据缺口，不等同于在 R0 中认证全部 API。

后续采用的 Q-19 直接以包路径表达成熟度，Q-20 则把晋升证据放入可执行测试、固化数据和生成元数据，不再维护逐 API 的独立成熟度清单。因此本问题的前提已经被替代，现标记为已作废；原采用方案作为历史记录保留。

## 建议的解决方案

### A1. R0 建立全量清单，但只认证首批函数 【已采纳】

#### 方案描述

列出全部公共 API，并记录契约状态、测试状态、参考来源、后端支持和成熟度。R0 只修复和验证首批基础函数，其余函数默认不得因为出现在清单中就被视为 stable。

#### 优点

- 尽早让真实承诺范围可见。
- 为后续按函数族认证提供统一工作台账。
- 清点与认证分离，不要求一次补完全部证据。

#### 缺点

- 即使不做认证，全量清点仍有一定文档维护成本。
- 成熟度标签如果没有面向用户展示，短期价值有限。

## 最终采用方案

A1. R0 建立全量清单，但只认证首批函数
