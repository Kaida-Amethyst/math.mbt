# Q-22. CI 是否区分纯 MoonBit 测试与外部 oracle 再认证 〔待讨论〕

> 最后更新日期：2026-08-13
> 仓库：Kaida-Amethyst/math.mbt
> 记录者：Codex

## 问题描述

`exp` 的固定测试语料由 MPFR 生成，但提交后只是普通 MoonBit 位模式数据。现有 CI 可以在不安装 MPFR 的情况下验证实现与固化语料一致，却不能证明这些参考值能够由记录的外部 oracle 重新产生。需要决定是否把两种含义不同的验证拆成独立 CI 状态，避免一个笼统的“测试通过”同时代表实现测试和 oracle 再认证。

本问题只决定 CI 的证据分层及每层绿灯的含义；运行频率、合并门禁和发布门禁由 Q-23 决定。

## 建议的解决方案

### A1. 把常规测试、固定 oracle 再认证和全量困难输入审计分层 【建议采纳】

#### 方案描述

建立含义明确的三类 CI 状态：

1. `check / pure-moonbit` 只使用 MoonBit 编译并执行仓库中已经固化的契约与 oracle 语料，覆盖 wasm、wasm-gc、JavaScript、native 的 debug/release；绿灯表示当前实现仍满足已提交证据。
2. `reliability / <family>-oracle-recertification` 安装固定的外部 oracle 工具，重新生成固定语料并逐字节比较，然后运行相应 MoonBit 测试；绿灯表示参考语料来源可复现，且当前实现仍满足它。
3. `reliability / <family>-hard-case-audit` 对固定版本的 CORE-MATH 等更大困难输入集分批审计；绿灯表示当前实现通过了记录范围内的扩大攻击语料。

“纯 MoonBit”限定测试的编译和执行不依赖 C FFI、MPFR 或其他外部 oracle，不等同于 CI 完全离线；工具链和包依赖的下载属于另一个供应链问题。各状态名称、README 徽章和认证记录应保留上述含义，不能把三种绿灯合并宣传成“全部输入已经证明正确”。

#### 优点

- 使用者能够判断一次绿灯究竟验证了实现、参考数据来源还是扩大攻击语料。
- 普通用户和常规 CI 继续保持纯 MoonBit，不承担 MPFR、GMP 和 C 工具链依赖。
- oracle 可重复性不再只依赖维护者文字声明。
- 重型审计可以保留独立结果、工具版本、最大误差和见证，而不模糊日常兼容性测试。

#### 缺点

- CI 状态、工作流和故障排查路径增多。
- 需要固定并维护外部工具、语料版本和分批脚本。
- 多个绿色状态仍只是对应范围内的测试证据，不构成全输入形式化证明。
