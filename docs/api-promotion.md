# API 晋升规则

本文规定如何把 `Kaida-Amethyst/math/experimental` 中的公共能力晋升到根包
`Kaida-Amethyst/math`。后续函数或最小函数族的晋升都应遵循这里的流程。

晋升不是简单地移动文件，也不以“现有测试是绿色的”为充分条件。它表示维护者已经为
一组明确的语义和误差承诺建立了可重复、可审查且覆盖全部支持后端的证据。

## 1. 包路径表示成熟度

仓库使用物理包边界表达成熟度：

- `src/` 是 stable 根包，只导出已经通过本文门槛的公共 API；
- `src/experimental/` 容纳尚未完成认证的公共 API；
- `src/internal/<role>/` 容纳需要跨包复用、但不构成稳定公共承诺的内部实现；
- `src/test/` 是大型黑盒认证测试的独立包；
- `tools/oracle/<family>/` 是开发阶段使用的外部参考值生成器和审计工具。

依赖方向固定为：

```text
stable       ──→ internal
experimental ──→ stable
experimental ──→ internal
test         ──→ stable
```

stable 不得依赖 experimental。experimental 不应重新导出 stable API，而应在内部通过
根包调用它。`internal` 必须按职责命名，例如 `internal/fpbits` 和 `internal/ulp`，不建立
含义无边界的 `internal/utils`。

## 2. 选择晋升单位

晋升单位是能够保持上述依赖方向成立的最小依赖闭包，不一定恰好是一个函数。

优先选择满足以下条件的候选：

1. 不依赖 experimental 中的其他公共 API；
2. 或者它依赖的函数可以作为同一个紧密函数族共同认证；
3. 私有共享逻辑能够留在本文件，或迁入职责明确的 internal 包；
4. 函数的外部语义有标准、成熟库或公开数学定义可供裁判；
5. 能够获得独立于当前实现的参考证据。

若候选仍依赖不准备同时晋升的 experimental API，应停止晋升，而不是把这种反向依赖
带入 stable。

## 3. 先确定契约，再测试实现

晋升前必须先写清用户可以依赖的契约。裁判顺序是：

1. IEEE 754 和 C23 构成浮点基础语义底线；
2. 与 MoonBit Core 重叠的能力，以兼容 Core 作为生态目标；
3. 特殊函数再参考成熟数学库、实现来源和数学惯例；
4. 仓库原有文档和测试只能作为历史信息，不能自动推翻更权威的外部语义。

契约至少回答适用的以下问题：

- 定义域和返回值含义；
- NaN、正负无穷和正负零的行为；
- 是否保留 signed zero；
- 上溢、下溢和次正规数的行为；
- 舍入模式及准确度上界；
- 是否承诺 NaN payload、浮点异常标志或 `errno`；
- 单调性、奇偶性、值域等用户可以依赖的性质。

准确度只能承诺已有证据支持的上界。不得把“在当前样本中没有发现误差”写成“正确
舍入”，也不得用笼统的全局 epsilon 代替与问题相符的误差尺度。

## 4. 为函数选择合适的证据

所有晋升都需要契约和跨后端证据，并按函数性质提供适用的独立参考、性质与回归证据；
具体工具应随函数类型变化。

### 4.1 精确分类和位操作

例如 `isnan`、`isfinite` 或浮点位拆装，应使用显式 IEEE 754 位模式和边界枚举。结果应
逐位或逐布尔值相等，不需要为了形式统一而引入 MPFR。

### 4.2 精确舍入的基础运算

例如缩放、舍入和相邻浮点数操作，应以正确舍入的目标位模式为主要证据，重点覆盖
normal/subnormal 转换、signed zero、指数极值以及相邻输入。可以使用 MPFR 生成参考值，
但验收尺度通常是精确位模式，而不是宽松 ULP。

### 4.3 近似数值函数

例如 `exp`、`log` 和特殊函数，应使用独立高精度 oracle 计算固定参考值。普通有限结果
以 ULP 为主要尺度；接近零、消去和下溢区域按需要补充绝对误差；动态范围很大且远离零
时才考虑相对误差。

### 4.4 集合和复合函数

例如归约、范数和概率函数，除独立参考值外，还应覆盖空输入、非有限值组合、排列或缩放
不变量，以及数值稳定性相关的极端分布。

性质测试只能补充 oracle，不能代替 oracle。两个共享同一算法或同一错误来源的实现也不
构成独立证据。

## 5. 输入语料要求

候选函数的固定语料至少覆盖适用的以下输入：

- IEEE 754 的零、次正规数、正常数、无穷和 NaN；
- 正负号以及 signed zero；
- 每个实现分支边界及其前驱、边界值和后继；
- 定义域边界、上下溢边界和 normal/subnormal 转换点；
- 指数和尾数分层的固定种子随机位模式；
- 数学上有意义的特殊值和精确值；
- 外部攻击语料、差分搜索和历史缺陷发现的最坏案例。

样本数量和代码覆盖率用于发现缺口，但不能单独证明数值正确。发现的失败案例必须缩减并
固化；即使它仍在最终契约允许的误差内，也应保留达到最大误差的见证输入。

## 6. 测试与文件组织

一个已晋升函数的标准结构是：

```text
src/<family>.mbt
src/test/<family>/
├── moon.pkg
└── oracle_test.mbt
tools/oracle/<family>/
├── generate.c
├── Makefile
└── README.md
```

### 6.1 实现文件

`src/<family>.mbt` 按以下顺序组织：

1. 公共契约和参考来源；
2. stable 实现；
3. 少量、可人工审阅的契约测试。

契约测试适合检查特殊值、signed zero、关键边界和少数已知回归。它们虽然位于实现包内，
但应只通过公共函数验证行为，不依赖私有中间状态。

### 6.2 大型 oracle 测试包

每个函数的大型固化语料放在各自独立的测试包，例如：

```text
src/test/exp/oracle_test.mbt
src/test/scalbn/oracle_test.mbt
```

这些包通过 `@math` 调用根包公共 API，因此同时验证导出接口和外部调用路径。每个函数
单独形成编译边界，既避免根包源码随着认证数据膨胀，也避免所有固化数组被合并成超过
WebAssembly 单函数大小限制的测试初始化函数。

### 6.3 白盒测试

只有确实需要访问私有状态或验证内部不变量时，才保留 `*_wbtest.mbt`。旧样本如果已经被
契约测试和独立 oracle 完整覆盖，应删除，不保留多套来源不明的期望值。

### 6.4 外部生成器

MPFR、Arb、Python、C FFI 或外部攻击语料只能用于 `tools/oracle/` 下的显式生成和审计。
生成器应记录：

- oracle 名称和版本；
- 舍入模式；
- 精度策略和终止条件；
- 固定随机种子；
- 输入构成和样本数量；
- 外部语料的版本或提交号；
- 已知最大误差及见证输入。

固化数据使用 IEEE 754 位模式，而不是依赖宿主环境解析的十进制真值。生成器必须提供
可重复生成和逐字节比较的命令。

发布源码和常规 `moon test` 必须保持纯 MoonBit：不得在标准构建或测试中隐式调用
MPFR、C 运行库、Python、网络或子进程。普通用户不需要安装 oracle 工具。

## 7. 跨后端验收

候选函数必须在 wasm、wasm-gc、JavaScript 和 native 的 debug/release 模式下满足同一
公共契约和误差上界。基础命令为：

```sh
moon fmt
make -C tools/oracle/<family> verify
moon check --deny-warn

for target in wasm wasm-gc js native; do
  moon test --target "$target" --deny-warn
  moon test --target "$target" --release --deny-warn
done

moon info --target all
```

还应检查生成的 `.mbti`：根包只新增预期的 stable 接口，experimental 接口中不再保留
同名导出，internal 辅助函数也不得意外出现在根包接口中。

如果不同后端产生不同位模式，但都满足误差上界，仍必须记录差异并判断它是否适合作为
stable 行为。不得只运行一个后端后推断其他后端正确。

## 8. 实际晋升步骤

一次晋升按以下顺序执行：

1. 审计候选及其完整依赖，确定最小晋升单位；
2. 根据权威来源修订契约，暂不以现有实现行为倒推契约；
3. 建立独立 oracle、边界语料、性质测试和外部攻击审计；
4. 修复任何违反契约或误差上界的实现问题；
5. 把共享底层实现迁入职责明确的 internal 包；
6. 把实现移入 `src/`，把大型语料放入 `src/test/`；
7. 将 experimental 中的调用者改为单向调用 stable API；
8. 删除 experimental 中的同名导出和已经被新证据取代的旧测试；
9. 更新公共文档、生成接口和 oracle 认证记录；
10. 完成全后端 debug/release 验证后交付审阅。

以下任一情况都应阻止晋升：

- 契约仍有未决语义；
- stable 将依赖 experimental；
- 参考值只来自当前实现或其同源移植；
- 任一支持后端超出承诺误差；
- 发现的失败或最大误差案例没有固化；
- oracle 不能重复生成，或发布测试依赖外部工具；
- 文档、源码位置和生成接口表达的成熟度不一致。

存在已知但处于公开误差界内的误差不必阻止晋升，前提是契约没有夸大、见证输入已经
固化，并且所有后端都满足同一上界。

## 9. `exp` 晋升实例

`exp` 是第一份完整范例，其最终结构为：

```text
src/exp.mbt
src/internal/fpbits/
src/test/exp/oracle_test.mbt
tools/oracle/exp/
```

### 9.1 依赖整理

原实现位于 experimental，使用同包的高低字拆装函数。晋升时没有把通用工具文件一起
公开，而是建立 `internal/fpbits`，使 stable 能复用位操作，同时不把它们承诺为用户 API。
experimental 中依赖 `exp` 的函数统一改为调用 `@math.exp`。

### 9.2 契约

`exp` 最终承诺：

- NaN 输入返回 NaN，但不承诺 payload；
- `+∞` 返回 `+∞`，`-∞` 返回 `+0`；
- `+0` 和 `-0` 都精确返回 `1.0`；
- 有限输入不产生负结果或负零；
- 在 IEEE 754 binary64、round-to-nearest ties-to-even 下，每个有限输入的结果与精确实数值正确舍入
  后的结果相差不超过 1 ULP；
- 不承诺 `errno` 或浮点异常标志。

实现文件底部只保留特殊值、有限极值和上下溢舍入转换点等小型契约测试。原有普通十进制
样本白盒测试在 MPFR 语料建立后删除。

### 9.3 独立 oracle

开发工具使用 MPFR 4.2.2。它从 128 位精度开始，分别向下和向上计算结果；只有区间两端
在 round-to-nearest ties-to-even 下得到同一个 binary64 位模式时才接受该参考值，否则
继续提高精度。这样不依赖任意固定精度，也避免二次舍入把错误结果固化为真值。

默认语料固化了 24,697 个输入和期望位模式，包括：

- IEEE 754 分类；
- 实现分支和参数规约边界；
- 上溢、下溢及次正规转换点；
- 全部有效参数规约单元的边界邻域；
- 三种固定种子分层随机输入；
- 外部审计找到的最大误差见证。

此外，认证阶段按十批检查了指定版本 CORE-MATH `exp` 攻击语料中的 1,129,371 个非 NaN
输入。分批是为绕开百万级 MoonBit 字面量导致的 native 链接范围限制，不改变输入集合。

### 9.4 准确度结论

审计发现以下最大误差见证：

```text
input bits    = 0xc086f6872b5f94e6
MPFR result   = 0x0000000000003b15
actual result = 0x0000000000003b14
error         = 1 ULP
```

因此 `exp` 可以承诺“不超过 1 ULP”，但不能承诺“始终正确舍入”。四个支持后端对该见证
返回相同位模式，全部默认语料也在 debug/release 下满足同一误差界。

这个例子说明晋升的目标不是证明实现完美，而是建立一个没有夸大、能由独立证据持续检验
的稳定契约。

## 10. 审阅清单

每次晋升提交审阅前，应逐项确认：

- [ ] 晋升单位及其依赖闭包已经明确；
- [ ] stable 不依赖 experimental；
- [ ] 契约依据裁判顺序写清，且没有由现有错误行为倒推；
- [ ] 特殊值、signed zero、定义域和上下溢行为已测试；
- [ ] 误差尺度与函数类型相符；
- [ ] 参考证据独立于当前实现；
- [ ] 分支边界、相邻浮点数、分层随机输入和最坏案例已覆盖；
- [ ] 大型 oracle 位于独立的 `src/test/<family>/oracle_test.mbt` 测试包；
- [ ] 外部生成器位于 `tools/oracle/<family>/`，且可以逐字节再生成；
- [ ] 普通构建和测试保持纯 MoonBit；
- [ ] 无独特价值的旧白盒或手写十进制样本已经删除；
- [ ] wasm、wasm-gc、JavaScript、native 的 debug/release 全部通过；
- [ ] `.mbti` 只发生预期的公共接口变化；
- [ ] README、API 文档和源码包路径表达相同的成熟度；
- [ ] 没有把样本内表现夸大成未经证明的全域保证。
